# 0016 — PDF export through a printable HTML view, not a server-side renderer

Status: accepted
Date: 2026-10-25
Related: [0009](0009-test-case-snapshots-in-runs.md),
[0010](0010-polymorphic-traceability-links.md)

## Context

S3-F1 adds exports. Customers send two artefacts outside the product: the
traceability matrix (to auditors) and a run summary (to clients and release
managers). CSV covers spreadsheets and tooling; people also ask for "a PDF".

Generating a PDF on the server is not a library call. The realistic options
render HTML in a headless browser, which brings a large binary, a sandbox to
harden, memory per render, a job runner once renders are slow, and a new
surface where tenant data is turned into executable markup.

## Options evaluated

| Option                                     | Fidelity                         | Operational cost                                                                           | Security surface                                                    |
| ------------------------------------------ | -------------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| Headless Chromium (Puppeteer/Playwright)   | Pixel-identical to the web       | ~150 MB image layer, CPU/RAM per render, needs a queue (debt 3: no job runner), sandboxing | A browser on the API host rendering tenant-controlled HTML          |
| PDF library (pdfkit, pdf-lib)              | Manual layout, poor tables       | Small, but every layout is hand-written code                                               | Small                                                               |
| External rendering service                 | Good                             | Another vendor, data leaves our infrastructure                                             | Data processing agreement; contradicts "no external providers" (S3) |
| **Printable HTML + browser "Save as PDF"** | Good for tables, user-controlled | None: React pages with a print stylesheet                                                  | Same as the rest of the web client (React escaping, CSP)            |

## Decision

1. **No PDF is generated by the API.** The web client has two print-only
   routes, `/print/traceability` and `/print/test-runs/:runId`, rendered
   without the app chrome, with a `@media print` stylesheet (repeated table
   headers, rows that do not split) and a "Print / Save as PDF" button that
   calls `window.print()`.
2. The print views read the **same authenticated endpoints** as the normal
   pages, so they inherit tenant isolation, project permissions and RLS. They
   do not need a new endpoint and they cannot show more than the user can
   already see.
3. The run summary is built from the run's **case snapshots** (ADR 0009), like
   the run CSV, so a later edit of a case never changes a past report.
4. Showing the print links requires `data.export`; the data itself is guarded
   by the read permission of each endpoint, as in every other page.

## Consequences

- Zero new dependencies, binaries or background work. The PDF a user saves is
  as good as their browser's print engine, which for tables is good.
- The output is not reproducible byte for byte and cannot be emailed or
  scheduled by the server. Scheduled or signed PDF reports need a renderer and
  a job runner; that becomes a new decision when a customer needs it.
- Printing is not audited (the browser does it); CSV exports are. The audit
  trail records the data leaving through the API, not every screen render.
- Revisit when: a scheduled/emailed report, a signed audit PDF, or a branded
  layout is required.
